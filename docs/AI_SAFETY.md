# AI reliability and review workflows (M5)

AI mode is optional. Deterministic mode makes no provider calls. Unknown provider names fail closed; mock providers are prohibited in production. Remote provider calls remain text-only and cannot invoke tools or select projects.

All application completions use the gateway. Both prompt strings pass through email, phone and long numeric identifier redaction. This is pattern-based minimization, not a guarantee that arbitrary confidential prose is anonymized. Inputs are limited to 24,000 characters, responses to 16,000 characters, provider calls to 60 seconds, and transport retries to at most three (environment settings control limits). Groq caps output at 2,048 tokens. Incomplete provider output is rejected.

Each attempted request reserves an `llm_calls` row under a project write lock before transmission. Successful, failed and interrupted requests consume the configured project request budget (default 50); historical non-cache `llm_logs` also count. New accounting rows contain only scope, model, hashes, status, timing and usage, never prompt or completion bodies. Legacy rows remain intact and are never used as cache entries. Minimal accounting is retained until project purge so retention cannot reset the lifetime request budget.

`LLM_RUN_TOKEN_BUDGET` defaults to 100,000. Each attempt reserves prompt UTF-8 byte length plus the 2,048-token output allowance, a conservative admission estimate rather than measured usage. Known nonnegative provider-reported usage replaces that estimate. Missing usage, failed requests and worker interruption retain the reservation with nullable measured counts and `reserved_unknown` provenance. Retries and recovered workers share the persisted run budget. Calls outside a run use a project-wide token budget. Reports show provider-reported and unknown usage separately. Configured-price estimates are separate from token counts and are never described as provider invoices.

Validated testability/conflict responses may be cached only inside a sealed run context. Cache keys include owner, project, sealed input hash (artifact hashes and edits), analysis versions, provider/model, exact redacted prompt hash and schema version. Schema and occurrence/reference checks run before caching and again on every hit. Malformed, wrongly scoped or expired entries are removed and fetched afresh. Rewrite generation and semantic review omit a cache schema version and bypass caching. Cached response bodies remain in their redacted provider form; confidential prose can still remain, so the cache is private project data, not anonymized public data.

`LLM_CACHE_TTL_SECONDS` defaults to 86,400 (one day), permits at most seven days, and zero disables caching. Expired entries are never served. Writes remove expired entries for that project. For inactive projects, schedule `python scripts/prune_ai_cache.py --apply` from `backend/`; omit `--apply` for a dry run. Project purge deletes both cache and accounting records. A cache hit records zero provider tokens and does not consume the provider-request budget.

Deployment requires stopping old API/workers and running `alembic upgrade head` before restarting. Migrations through `20261104_ai_workflows` are additive and does not reinterpret or delete historical logs. No existing user database was migrated during development.

Testability responses require strict fields and exactly one result per submitted occurrence ID. Repeated authored IDs are mapped by occurrence and source. Conflict results reject unknown IDs, self-pairs and duplicates. Each reported conflict is a candidate for human review, and an empty list is not proof that the document is consistent. Inputs are batched using conservative UTF-8 byte token estimates and a response-size item cap. Every occurrence and pair must be acknowledged exactly once; negative testability and conflict findings require exact nonempty source quotes. Oversized individual items produce partial analysis rather than being truncated.

Rewrite retries retain the original requirement. Checks cover normative structure, actor, numbers/units, negation/exception markers, original terms, and deterministic rules using classification inferred from the original text. These conservative lexical checks can reject valid paraphrases and cannot prove equivalent intent. All suggestions require human review; none is applied automatically. The report shows the individual checks. Missing metrics must be obtained from a stakeholder; invented thresholds do not pass. Provider or budget failure makes requested AI analysis partial. Worker cancellation/lease loss is never swallowed by repair.

## Monetary admission budgets

`LLM_RUN_COST_BUDGET_MICROUSD` defaults to 1,000,000 micro-USD (USD 1) per run. Zero explicitly disables the money cap. `LLM_PRICING` maps the exact `provider/model` to `input` and `output` rates, each expressed in micro-USD per **million** tokens. For example, a configured USD 0.10/million rate is the integer 100,000. Supply verified rates for your provider/model; no market pricing is hardcoded or inferred.

Prices and the monetary cap are snapshotted when a run is sealed. Each attempt atomically reserves the prompt-byte estimate and output-token allowance at those prices, rounding upward to whole micro-USD. Provider-reported usage releases the unused reservation and produces a configured-price estimate. Failed, timed-out or interrupted requests retain the full reservation. Missing/invalid prices or old unpriced attempts fail closed when the money cap is enabled. Cache hits are free of provider charges. Concurrent PostgreSQL callers are tested against the last allowance. Provider fees, taxes, discounts and later price changes are not represented; these are admission controls, not billing reconciliation.

## Batching and coverage

`LLM_BATCH_INPUT_TOKENS` defaults to 6,000 conservative UTF-8-byte token estimates; `LLM_BATCH_ITEMS` defaults to 12 and is capped at 20 to bound completion size. Global request, token and monetary budgets still apply across batches and worker attempts. Earlier validated batch findings are retained if a later call fails. Reports display reviewed/total counts for testability, conflict pairs and rewrite attempts. A partial stage prevents a final grade.

Conflict candidate generation deliberately enumerates every pair instead of applying an unvalidated retrieval heuristic. This guarantees no candidate-filter omissions, at quadratic cost. Large projects can hit the budget before all pairs are reviewed; their coverage stays explicitly partial. An acknowledged pair is a model review, not evidence that no real conflict exists. The six-requirement synthetic benchmark has 15 candidate pairs and two labelled conflicts: candidate recall is 2/2. This is not model detection accuracy or a representative production benchmark.

## Rewrite evidence and human decisions

Repair context includes the original requirement, corrected class/subtype when available, source location, neighbouring requirements and related conflicts. Retries stay anchored to the original. Deterministic checks preserve actor, quantities/units, negation, conditions and exception clauses. A separate semantic-comparison request assesses actor/action/object/scope and invented constraints; it must quote the original and proposal exactly. Semantic agreement remains advisory and never authorizes application. Uncertain or unsupported rewrites remain for human review; unknown thresholds must be supplied by a stakeholder.

The report offers **Reject suggestion** and **Apply to draft**, with an editable proposal and explicit intent/threshold/condition confirmation. Accepted or edited proposals create append-only `suggestion_decisions` and update only a draft based on the selected report. Applying requires the current draft edit version and unchanged source lineage/text. Ambiguous, missing, replaced or already-edited requirements are rejected; another draft branch is not silently reused. Request idempotency and decision-version checks prevent duplicate or stale decisions. The draft's extraction confirmation is cleared, so it must be reviewed and analyzed again. Original reports and scores remain immutable. Rejection records a decision without editing content. Project purge removes these decision records and idempotency receipts.

## Evaluation and release limits

Run `python backend/scripts/evaluate_ai.py` for the offline synthetic benchmark (also in CI). At this checkpoint it enumerates all 15 pairs, includes both labelled conflicting pairs, and blocks all four unsafe rewrites (meaningless text, dropped negation, invented metric and dropped exception). Schema tests reject unknown/dropped IDs, incomplete pair coverage, fabricated quotes, malformed cache entries and prompt-injection outputs containing extra tool/project fields. No tool execution path exists in the provider interface.

Opt-in live evaluation is available as `python backend/scripts/evaluate_ai.py --live --allow-external-fixtures`. It sends only the checked-in synthetic fixture, uses a disposable database, applies configured budgets, and reports coverage, usage and conflict precision/recall. A partial live evaluation exits nonzero. Configure a real provider and verified model prices first. This command was **not** run with a live provider during implementation.

M5's implementation and automated contract gates are complete. Live-provider quality, independent annotation, production-scale cost/latency and adversarial generalization remain M8 release-qualification measurements. Regex redaction is not comprehensive anonymization, lexical/semantic checks are not proof of intent preservation, and no current test establishes production accuracy or a 10/10 product rating.
